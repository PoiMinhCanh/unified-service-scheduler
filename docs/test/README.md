# Ticket tests and verification

Use `docs/test/` for ticket test scenarios, reproducible manual checks, and observed verification results. Executable tests belong in the application's test projects; Markdown checklists supplement them and do not replace automated business, persistence, or concurrency tests.

> [!NOTE]
> The ticket 1 application/test projects, SQL Server fixtures, and execution report exist; ticket 2 adds real Redis fixtures plus discovery/catalog/availability verification; ticket 4 adds real Collector/Prometheus/Tempo/Grafana fixtures plus telemetry delivery, provisioning, outage, and workload verification. Templates describe expected checks; passing results require actual execution evidence.

## Files and naming

| File | Purpose |
| --- | --- |
| [[test/backend-test-template\|Backend test template]] | Per-ticket requirement coverage, unit/API scenarios, manual checks, and execution results |
| [[test/integration-test-template\|Integration test template]] | SQL Server, Redis, migrations, permissions, concurrency, and operational verification |
| `<ticket-number>-test.md` | Requirement coverage and executed automated/operational evidence recorded during implementation |
| `<ticket-number>-manual-test.md` | Manual API/operational instructions generated by the orchestrator `test` phase, with human execution records when available |

Tickets live directly in `docs/tickets/`; their test reports live directly in `docs/test/` using the per-ticket filenames above.

## Phase responsibilities

- **Plan:** Define test coverage, implementation steps, commands, dependencies, expected outcomes, and pass criteria. Run existing tests only when useful for a baseline; planning does not prove new behavior passes.
- **Implement:** Write tests with code, run relevant checks as steps finish, complete required automated/operational verification for the selected scope, and record evidence in `<ticket-number>-test.md`. Resolve failures and rerun affected checks, including after review fixes. Required failures or blockers prevent implementation completion.
- **Test:** Generate `<ticket-number>-manual-test.md` using the create-manual-test skill. Inspect implementation and recorded results to produce accurate instructions; do not execute tests or change application/test code. New cases remain Not run or Blocked. Link the checklist and implementation report without overwriting prior results.

Manual execution belongs to the human tester. Record Passed/Failed only from actual execution evidence, preserving revision, environment, actions, observations, and any prior records. A generated checklist completes the generation phase but does not establish ticket acceptance or replace automated verification.

## What to verify

Use the current ticket's requirements, acceptance criteria, and verification cases as the test baseline. Use [[architecture]] for domain rules and API behavior. Keep scenario definitions in the ticket and record execution evidence in its test report; extend coverage when behavior changes.

- **Unit tests:** pure scheduling rules, qualification and active-state decisions, interval boundaries, duration, and time handling using controllable time.
- **API and database integration:** request/response contracts, validation, persisted associations, dealership scope, migrations, booking procedures, and denied direct appointment writes using the runtime identity.
- **Concurrency:** overlapping technician and bay reservations through independent connections; verify both responses and final SQL Server state.
- **Redis integration:** miss, hit, expiry, invalidation, and outage fallback without weakening SQL Server booking validation.
- **Operational checks:** restart persistence, database-outage readiness, telemetry correlation, and clean-checkout execution. Manual inspection supplements automation.

Use the ticket's selected xUnit, WebApplicationFactory, and Testcontainers stack as projects are implemented. SQL Server tests must use real SQL Server; EF's in-memory provider and SQLite do not verify its locking, stored procedures, or permissions. Use synthetic data and isolated environments with project-specific endpoints and credentials.

## Keeping records current

Read the ticket, research, plan, and actual changes before writing scenarios. Record setup, data, actions, expected outcomes, and cleanup. Use actual commands and project paths once they exist; mark proposed ones as pending rather than presenting them as executable.

Record the revision, environment, executed command, observed result, and evidence. Use Passed, Failed, Not run, or Blocked with a reason. Keep planned expected outcomes separate from observed results; unchecked cases remain unexecuted. A successful build alone is not proof of booking correctness.

For schema changes, follow [[database/maintenance|Database maintenance guideline]]. Link relevant [[plans/README|plans]], [[review/README|reviews]], and [[deploy-notes/README|deployment notes]] instead of duplicating their instructions.

Use Obsidian-compatible Markdown with `title` and `tags` frontmatter and internal wiki links. Keep each paragraph and list item on one line. Preserve code blocks, diagrams, tables, and nested expected-result lists.
